# 4× CPU 降速：final 同步 flush 压测

这是优化前的同步 flush 基线。当前分帧实现与同输入对照见 [预算收尾验证](./streaming-finish-budget-results.md)。

2026-11-02，Chrome 156.0.8078.74，生产构建，1100×900。每组正常速度与 4× 降速各 3 次，正反顺序交错，共 24 次。

## 结论

当前全量渲染配置下，4× CPU 降速的四组场景均在 3/3 次运行中出现 final 窗口长任务。最大 RAF 回调间隔的中位数从约 71ms 到 920ms，存在明显的主线程卡顿与掉帧风险。**不能把任意体量的积压同步 flush 当成无卡顿的“瞬间完成”。**

上一轮约 3ms 的结果来自小输入，不适用于本次长文本和大包。2 万字符纯文本的 Vue/DOM 提交约 22ms，但后续布局约 34ms，整体任务仍达到约 70ms；只计 nextTick 返回时间会漏掉这部分成本。

## 4× 结果

| 场景 | 初始字符 + 追加字符 | final 提交 ms | 结束附近最大回调间隔 ms | 最长 Long Task ms | 有长任务的运行 | 最坏回调间隔 ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |

## 同输入 1× / 4× 对照

| 场景 | 1× final 提交 ms | 4× final 提交 ms | 1× 最大回调间隔 ms | 4× 最大回调间隔 ms | 1× / 4× 有长任务的运行 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 2 万字符纯文本末包 | 5.2 | 21.9 | 17.8 | 70.7 | 0/3 / 3/3 |
| 约 2 万字符历史 + 约 4 千字符增量 | 55.3 | 298.3 | 59.0 | 375.9 | 2/3 / 3/3 |
| 三个约 8 千字符 Markdown 大包 | 85.3 | 502.5 | 100.7 | 531.6 | 3/3 / 3/3 |
| 约 5 万字符 Markdown 末包 | 106.7 | 771.2 | 144.3 | 919.7 | 3/3 / 3/3 |

较大的 Markdown 大包在正常速度下也会产生长任务。CPU 降速还会改变输入期间的出字进度，因此 final 时的积压不一定相同，不应把两列比值理解为纯计算速度倍率。

## final 窗口的布局与绘制

| 场景（4×） | final 时未显示的 DOM 文本字符 | final 前活跃词节点 | 最终元素数 | Layout ms | Paint ms | 回调间隔 p95 ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 2 万字符纯文本末包 | 20000 | 0 | 7 | 34.0 | 2.0 | 17.7 |
| 约 2 万字符历史 + 约 4 千字符增量 | 1898 | 248 | 2881 | 43.4 | 7.0 | 18.8 |
| 三个约 8 千字符 Markdown 大包 | 22179 | 133 | 2923 | 66.5 | 8.2 | 18.0 |
| 约 5 万字符 Markdown 末包 | 46836 | 0 | 5875 | 97.6 | 4.0 | 18.9 |

“未显示字符”按最终静态渲染的 textContent 与 final 前 textContent 的长度差计算，不包含 Markdown 标记。纯文本末包和 5 万字符末包在 final 前没有活跃词动画，仍然产生长任务，因此问题不能仅归因于取消 fade；一次性的解析、DOM 更新和文本布局也会阻塞主线程。这里没有额外 CPU profile，不能把 final 提交时间进一步精确拆成解析与 Vue 更新两部分。

**p95 只有约 18–19ms 仍不能证明 final 顺滑。** 每次只有一个特别长的阻塞区间，随后的一秒观察期包含许多正常帧，p95 会掩盖该尖峰。应关注跨 final 的最大间隔、Long Task 和单次最坏值。

## 口径与限制

- 通过 CDP `Emulation.setCPUThrottlingRate({ rate: 4 })` 在每次导航后应用降速；这是 CPU 模拟，不是 GPU 降速，也不等价于某款真实低端设备。
- 使用当前工作区源代码构建。`fade=true`、`smoothStreaming=true`、`flushOnFinish` 为默认 true、`parseCoalesceMs=0`；关闭虚拟化、批量挂载、视口优先与延迟节点，和上一轮全量渲染配置一致。启用虚拟化的应用可能不同。
- 初始历史与完整静态参考在测量前渲染；测量前请求 GC，并滚动到初始内容尾部。测量中没有继续自动滚动；Paint 仅反映当时视口的绘制，不能代表最终文档所有像素的成本。
- 每帧仅记录 performance.now 与 RAF timestamp，不扫描 DOM。DOM 文本长度和节点数只在关键阶段读取，避免上一轮每帧扫描对大文档的干扰。trace 和这些少量采样仍有开销。
- `final 提交`：设置 final 到 Vue nextTick 返回，不包含之后全部布局、绘制与屏幕显示延迟。
- `结束附近最大回调间隔`：RAF 回调实际执行时间之间的间隔，窗口包含跨越 final 标记的那一段。它可能含最后一次 chunk 的工作；这是渲染器响应性的代理指标，不是 GPU 实测丢帧数。原始 RAF timestamp 间隔也保存在 JSON 中。
- Long Task 由 PerformanceObserver 收集，包括与 final 标记重叠或之后发生的任务；因此可能包含最后一次输入和随后布局，不能把它全部当作 flush 函数独占时间。
- final 后等待两个 RAF 回调，再观察一秒，覆盖同步提交之后的布局、绘制及后续任务。final 窗口内 Trace 的 Layout/Paint 事件按重叠计入，指标可能嵌套或并行，不能相加作为总 CPU。GPU 时间、电量未测。
- 所有 24 次运行都在 final 提交时得到与静态渲染一致的完整文本，活跃词节点为 0，观察结束无运行中动画、无浏览器异常。正确完成不等于没有卡顿。

## 本轮范围与后续判断

本轮仅增加测量脚本、原始结果和报告，未改变渲染策略。数据表明，大积压下需要限制单帧的解析与挂载工作量；可以保留“结束时立即停止 fade”的语义，但不能仅靠同步 flush 来保证不卡顿。具体分批、虚拟化或解析卸载方案需要单独实现并验证，不能从这三次样本直接确定一个通用字符阈值。

## 复现

```sh
node scripts/benchmark-streaming-finish-cpu4x.mjs
```

脚本构建当前版本，在端口 4202 启动临时预览，测量后关闭浏览器与服务。结果写入 `.tmp/stream-finish-cpu4x/results.json`，每次运行的完整 Chrome trace 为同目录 `trace-<场景>-<倍率>x-<次数>.json.gz`，解压后可导入 DevTools Performance。
