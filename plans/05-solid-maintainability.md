# 05：降低 Solid 长期维护成本

优先级：内部重构可后续；新增公共导出的边界应在发布前审核。不能以此计划拖延已明确的功能修复，也不要求本次 PR 零重复、零 any。

## 债务与处理原则

### 公共类型与导出边界

`src/index.ts` 暴露大量内部 helper 和测试相关入口；`CustomComponentMap` 使用 `Component<any>`，节点消费广泛依赖强制转换。运行时能通过不代表用户能从类型准确理解支持范围。

1. 按使用场景区分正式公共 API、兼容别名、内部实现和测试 hook，先核对消费者及实际发布状态。
2. 优先收紧公共 props、回调 payload 和自定义 renderer 类型，添加类型消费用例；避免用宽泛索引签名接受任意无效参数。
3. 审核 `resetCodeBlockRuntimeReadyForTest` 等导出是否确需公开。已对外承诺的入口按兼容策略处理，不直接删除。
4. 替换复杂条件推导和反复 `as any` 时，优先引入准确的 runtime adapter 接口，不尝试一次清除所有动态 parser 节点兼容代码。

验收：公开声明能表达真实行为，示例类型检查通过；不能为了“类型漂亮”丢失合法自定义节点扩展能力。

### 模块组织与可审查性

普通节点集中在长行 JSX，renderer 测试超过千行，代码块逻辑同时处理异步 runtime、选择区、主题、fallback 和工具栏。

1. 先按行为拆分测试为基础节点、流式、图表、生命周期和扩展，复用少量测试工具，不改变断言强度。
2. 将难审查的长行 JSX 正常展开；按实际职责拆模块，不为每个单行函数创建文件。
3. 有独立验证支撑后再提取 editor 同步与选择区逻辑，保留调用顺序和生命周期语义。

验收：相关测试数量及有效覆盖不缩水，公共入口不意外改变；结构整理与行为修复尽量分开 diff，方便 reviewer 识别风险。

### 跨框架重复逻辑与同步策略

Solid 复制了 HTML 渲染/增强、安全处理、Worker、CSS 和部分 playground 算法。机械移植期间可接受，长期没有同步方式会导致修复只落到一个框架。

1. 记录副本来源和基线，列出安全处理、Worker 协议、optional loader 等高风险同步点。
2. 优先共享测试输入和行为断言，建立跨框架对照；先发现分歧，再决定是否提取代码。
3. 仅对确认无框架依赖、行为一致且有共同测试的纯逻辑提出共享模块方案。Solid 生命周期和 JSX 留在包内。
4. CSS 与框架 namespace 的转换规则保持可解释；不要全量盲目同步，覆盖 Solid 特有修复。

验收：后续修改关键共享行为时，有明确的受影响框架清单和验证入口。不要求本轮减少到唯一实现，更不扩张成全仓 renderer 引擎重写。

## 执行边界

每一批先说明可维护性收益、涉及文件和不变行为，再做最小整理。内部重构用对应 unit/typecheck/build 验证；触及 runtime、Worker、HTML 或 CSS 时增加相关浏览器/安全回归。共享包调整或 API 破坏性变更另行确认，不自动提交或发布。
